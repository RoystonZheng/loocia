# Apollo 配置管理和接入

## 适用范围

用于滴滴内部 Apollo 配置同步平台的服务创建、配置查看、新增或修改、发布、回滚和应用接入。这里的 Apollo 不是携程开源 Apollo。

## 来源和时效

本次核对了 Cooper 官方文档，没有在 2026-08-11 对生产发布做实操验证。平台页面、部署绑定方式和语言 SDK 会变化。固定知识保留配置模型、操作边界和验收闭环；具体按钮、SDK 版本和环境地址以官方文档及平台当前页面为准。

## 核心概念

- 服务：配置管理和权限边界。创建服务时通常会创建同名 namespace。
- namespace：应用读取配置时使用的顶层标识。
- config：namespace 下的一组配置项。
- key/value：单个配置项及其值。
- Region：差异化配置和分级发布范围；`full_traffic` 是默认 Region 名称，不等于跳过灰度的一次性覆盖。
- 发布版本：已经下发给消费者的不可混淆事实。草稿不是生效配置。

## 必要输入

- 环境 `<ENV>`、服务 `<SERVICE>`、namespace `<NAMESPACE>`、config `<CONFIG>`。
- key、数据类型、合法范围、默认值或 fallback、消费方、Owner 和生效时机。
- 发布范围、灰度顺序、验证方式和回滚目标版本。
- 接入方式：SDK、HTTP，或经 Apollo 团队确认的组合方式。

## 平台和安全边界（MUST）

- 密码、AccessKey Secret、Token、私钥等敏感值不得进入 Apollo。敏感配置使用 KMS。
- 不从示例或其他项目复制 namespace、config、key 或 Odin 节点。
- 不把“保存草稿”当成“已发布”，也不只看平台页面而忽略消费端有效值。
- 不用删除 key 代替版本回滚。删除通知和客户端 fallback 行为必须事先设计。
- 不在未确认环境和发布范围时执行发布。

## 查看配置

1. 进入与目标环境匹配的 Apollo 配置同步站点。
2. 从“我的服务”或“全部服务”选择目标服务；无权限时申请最小所需权限。
3. 核对 namespace、config、Region 和发布状态。
4. 查看当前已发布版本、类型、最后修改人和发布时间，并与草稿区分。默认只在回复中给出元数据和脱敏结论；如果历史配置疑似包含敏感值，不展示或复制其原文。
5. 查看发布历史和灰度计划，确认目标机器或集群属于哪个 Region。
6. 在消费端核对实际版本和值。平台显示已发布不等于 agent 已落盘或应用已加载。

预期结果：能够回答“哪个环境、哪个版本、什么范围、应用实际读到了什么”，而不是只返回页面中的一个值。

## 新增或修改配置

1. 先定义 key 契约：名称、类型、范围、默认或 fallback、Owner、消费方和删除语义。
2. 关联 key 需要同时生效时，放在同一 config 和同一发布版本中，消费端按完整快照校验后原子替换。
3. 选择目标服务和 config。没有服务时先创建服务，明确配置类型和访问模式；不要为了一个项目复用无关服务。
4. 新增或修改 key，保存草稿，并检查与现有 key 的兼容性。
5. 选择 Region 和发布计划。先预发或小范围灰度，再逐阶段扩大。
6. 服务启用发布审批时提交审批；未启用时仍需遵守当前团队的发布确认规则。发布前向用户展示环境、范围、变更摘要、消费方验证和回滚版本。
7. 每个阶段验证应用日志、配置版本、关键行为和错误指标，验证通过后再继续。

## 应用接入

1. 选择访问模式。服务端常用 SDK；HTTP 适用于官方允许的直接读取场景；组合模式需与 Apollo 团队确认。
2. 完成服务权限、namespace 和部署信息绑定。线上 SDK 模式优先绑定实际部署服务节点，线下按平台要求登记机器。

### SDK 模式

1. 在运行机器安装 apollo-agent。容器部署需要保证 agent 在应用读取配置前就绪，必要时将依赖设置为阻塞。
2. 使用当前语言的官方 SDK，只初始化一次；读取时显式传 namespace、config 和 key。
3. 启动时加载完整快照，校验必需 key 和类型。不可缺失的配置应阻止错误启动；允许降级的配置应有清晰本地 fallback。
4. 团队建议监听 `ADD`、`UPDATE`、`DELETE`，新快照完全合法后再原子替换；非法更新保留上一合法版本并告警。
5. 记录版本、加载成功和降级状态，不记录敏感值。

### HTTP 模式

1. 从当前官方“配置 HTTP 接口”文档获取与环境匹配的 Server 域名或 VIP、鉴权方式、请求参数和返回结构，不从其他项目复制。
2. 请求显式携带 namespace、config、Region 等官方要求的定位参数，并设置有限超时和重试上限。
3. 解析并记录响应版本或等价标识，校验配置完整性后再替换本地快照。
4. 定义请求失败、旧版本、删除和非法值的缓存或 fallback 行为；不让高频业务流量直接依赖未评估的管理接口。
5. 用目标环境的真实消费端验证返回范围和值已经生效，回复中只提供元数据和脱敏结论。

### 组合模式

只有 Apollo 团队确认支持并给出接入方案时使用，按专项方案验收，不自行拼接 SDK 和 HTTP 行为。

## 验收

- 平台已发布版本、Region 和目标节点正确。
- agent 或 HTTP 链路可用，应用能读取指定 namespace/config。
- 应用日志或指标能证明已加载目标版本。
- 新增、更新、删除、非法值和平台不可用场景符合约定。
- 灰度阶段的关键业务行为和错误率正常。

## 回滚和排障

- 配置导致异常时优先使用平台发布历史回滚到上一已验证版本。
- 回滚后仍需核对消费端已加载回滚版本，不能只看平台状态。
- 机器未收到配置：核对环境站点、访问模式、部署绑定、Region、agent 安装和落盘权限。
- 应用读不到 key：核对 namespace/config/key 大小写、发布状态、目标 Region 和 SDK 参数。
- 删除后行为异常：恢复上一版本，并修复客户端删除或 fallback 语义。

# KMS 凭证管理和接入

## 适用范围

用于 KMS 中敏感信息托管凭证的创建、元数据查看、应用接入和版本轮转。业务数据加解密使用同一平台，但算法和密钥生命周期应另写专项 runbook。

## 来源和时效

本次核对了 Cooper 官方文档，没有在 2026-08-11 对生产凭证创建或轮转做实操验证。KMS 环境、接入网关、SDK 和审批流程会变化。具体地址和版本以官方接入地址页及当前平台为准。本手册不保存任何真实 AccessKey Secret、凭证值或项目资源坐标。

## 核心概念

- 环境：线下、国内线上和其他区域相互隔离，资源不能默认复用。
- 项目组：资源和权限隔离边界。
- AccessKey ID/Secret：SDK 身份认证信息。Secret 只在安全注入链路中使用。
- CMK：保护凭证内容的主密钥。
- Credential/Secret：托管敏感值的资源，包含 Secret ID 和版本。
- Version：凭证值的明确版本。运行时获取敏感信息必须显式传版本号。

## 必要输入

- 环境 `<ENV>`、项目组 `<PROJECT_GROUP>`、凭证用途和 Owner。
- 凭证类型、编码契约、CMK、访问身份和最小权限范围。
- 新旧 Version、消费方、切换顺序、验证方式和失效计划。
- 应用接入方式、运行区域和对应 KMS endpoint。

## 平台和安全边界（MUST）

- 不在代码、配置、文档、Issue、日志或回复中保存 SecretKey、凭证明文或解密结果。
- 不把敏感值放入 Apollo 代替 KMS。
- 不跨环境或跨项目组猜测复用 AccessKey、CMK、Secret ID 或 endpoint。
- 独立 SDK 和 Agent 两种接入形态不在同一项目中混用。Agent 方式必须同时使用 KMS Agent 和对应 Agent SDK，不能把“只装 Agent”当成完整接入。
- 获取托管凭证时必须显式传 Version。无版本的“取最新”可能受缓存或定时刷新影响。

## 新增凭证

1. 进入目标环境的 KMS 管控台，选择或创建正确项目组。
2. 确认项目组管理员和审批路径可用，按最小权限创建或复用 AccessKey 身份。
3. 选择或创建用于保护凭证的 CMK，核对算法、用途和状态。
4. 在凭证管理中创建“自定义凭证”，填写不泄露实际值的名称、用途和 Owner。
5. 按官方自定义凭证契约，对敏感值做一次 Base64 编码后写入。消费端取回后只解码一次，并用受控测试验证原值一致。
6. 保存非敏感坐标：环境、项目组、Secret ID、Version、用途和 Owner。不要保存凭证值或 AccessKey Secret。
7. 需要审批的更新或授权按平台流程提交，由独立审批人完成。

预期结果：凭证有明确环境、项目归属、CMK、Version、授权和审计记录，明文没有进入代码仓库或普通文档。

## 查看凭证

1. 默认只查看环境、项目组、名称、Secret ID、版本列表、当前状态、授权、更新时间和审计记录。
2. 核对应用配置引用的是明确 Version，而不是只记录 Secret ID。
3. 只有业务任务确实需要且权限允许时，才由受控应用或官方工具获取值；不要在对话或截图中展示明文。
4. 查看结果只记录元数据结论，例如“目标版本存在且已授权”，不记录值本身。

## 应用接入

先选择一种官方接入形态，并记录选择理由。同一项目不得混用。

### 独立 SDK

1. 使用与运行环境和区域匹配的 KMS Server endpoint。测试网关、办公网地址和生产网关不能混用。
2. 通过安全注入提供 AccessKey ID/Secret，不把身份信息提交到仓库。
3. 使用当前语言的独立 SDK 初始化超时、缓存、日志和可选 Redis。未启用 Redis 时不要初始化无关连接。
4. 启动时可预加载关键凭证；预加载失败是否阻断启动按依赖强度明确处理。
5. 调用 `SearchSecretValue` 或等价接口时显式传 Secret ID 和 Version。

### Agent 方式

1. 在 KMS 平台创建目标环境的项目组和 AccessKey，按官方 Agent 安装注册说明完成服务注册。
2. 线下机器按官方方式安装 KMS Agent；弹性云部署按平台当前方式启用 Agent 依赖并重新部署。
3. 使用 AccessKey 注册正确的机器 IP、部署节点和机房，确认凭证缓存已经下发到目标节点。
4. 应用引入与语言匹配的 Agent SDK，从 Agent 本地缓存读取，不再配置独立 SDK 的 KMS Server 直连流程。
5. 初始化 Agent SDK 的缓存路径、日志和超时，调用取值接口时仍显式传 Secret ID 和 Version。

### 两种方式的共同验收

1. 对自定义凭证返回值做一次 Base64 解码，校验格式和业务约束后再使用。不要把解码值写日志。
2. 明确失败策略。数据库密码等启动必需凭证获取失败应阻止错误启动；可降级场景必须有经过安全评审的 fallback，不能回退到仓库明文。
3. 健康检查要证明“取值并被依赖使用成功”，不能只证明 SDK 或 Agent 初始化成功。

## 版本轮转

1. 盘点全部消费方和当前 Version，确认旧版本失效后哪些旧镜像会无法启动。
2. 在上游系统生成新值或在 KMS 创建新版本，保持旧版本暂时可用。
3. 更新预发消费者引用的明确 Version，验证取值、解码和真实依赖连接。
4. 按发布流程切换生产消费者，监控错误率和依赖健康。
5. 全部消费者稳定后再将旧版本失效，并记录切换时间和证据。
6. 失效后，代码镜像回滚不等于配置回滚。旧镜像若引用旧 Version 会启动失败，必须准备兼容镜像或重新启用旧版本的受控方案。

## 失败处理

- 认证失败：核对环境、项目组、AccessKey 状态和授权，不输出 SecretKey 排障。
- 找不到凭证或版本：核对 Secret ID、Version 和环境，不改成无版本查询规避错误。
- endpoint 不可达：核对运行区域、网络和官方接入地址，不在生产容器使用测试网关。
- 解码失败：停止使用该值，检查创建时编码契约和版本，不做多次猜测性解码。
- 轮转后依赖失败：切回仍有效的上一 Version 或恢复上游旧值，验证消费者恢复后再分析。

# AI Cool Tool Discovery Requirements

## Clarified Requirements

AI Cool needs a first-release tools discovery and sedimentation module in the current ai-cool repository. The authoritative product baseline is Cooper document 2209600482571 section 5. That section overrides the older historical first-phase plan that described a read-only Git Markdown report import, GitHub Trending-style discovery, complex tool detail pages, or offline report ingestion. No production code should be implemented while this DevKit cycle is still in requirements, design, or plan generation.

The module must support one closed product loop: discovery configuration or manual repository add creates GitHub tool candidates; candidates are deduplicated by GitHub repository node_id and shown in the discovered tools list; a user can either mark a discovered candidate as not handled or start evaluation; evaluation is recorded by linking to a Cooper evaluation document that the user creates outside AI Cool; evaluation can finish as included or not included; only included tools appear in the team tools list. This loop must remain usable from the UI in the first release, including the discovery configuration page.

Tool status is limited to four internal values: discovered, evaluating, included, and excluded. The first release must not add an observe status. Discovered means the repository has been found and no evaluation decision has been made. Evaluating means a user has chosen to evaluate the tool and AI Cool has recorded evaluator, operator, start time, and Cooper evaluation document link. Included means evaluation is complete and the tool is admitted to the team tools list. Excluded means either a discovered tool was marked not handled or an evaluating tool was completed as not included; excluded tools are retained for deduplication and audit but do not appear in discovered, evaluating, or team primary lists.

GitHub keyword discovery must use the official GitHub Repository Search API. It searches English phrases in repository name, description, Topics, and README using queries equivalent to examples such as "coding agent" in:name,description,topics,readme, "agent skills" in:name,description,topics,readme, and "browser agent" in:name,description,topics,readme. Keyword discovery exists because many repositories do not maintain accurate Topics; its output is only a candidate set and never a recommendation or endorsement.

Each keyword discovery configuration has an initial limited baseline scan. After the first successful run, it must not repeatedly run full historical searches. Incremental runs use the configuration last_success_at as the checkpoint, with a 24-hour overlap to avoid scheduler delay and GitHub index delay. The implementation must run both created:>time searches for newly created repositories and pushed:>time searches for older repositories that have recently become active while matching the query. Within the overlap, duplicate results update recent hit time rather than creating new candidates.

GitHub Topic discovery must also use the official Repository Search API, using topic: qualifiers such as topic:ai-agents, topic:agent-skills, topic:model-context-protocol, and topic:browser-automation. Topic discovery is a focused category coverage mechanism, but because repository authors maintain Topics themselves it must not replace keyword discovery.

Manual add must let a team member paste a GitHub repository URL. AI Cool then calls the official GitHub Repository API, reads repository facts including node_id, and deduplicates against existing tools. Manual add exists for repositories found from articles, group chat, colleague recommendations, or browsing GitHub. The first release must not parse the GitHub Trending web page and must remove the old Trending page based discovery direction.

Discovery configuration must be user-facing in the first release. A configuration manages only keyword or Topic discovery, and one configuration maps to exactly one discovery method. Its fields are configuration name, discovery method, keyword terms or GitHub Topics, trigger type manual or weekly, enabled or disabled state, and run information including last run time, result count, and failure reason. The UI must let users create, edit, enable, disable, and manually run configurations. Advanced GitHub query parameters must not be exposed in the first-release UI. The system-level defaults are public repositories only, archived repositories excluded, forks excluded by default, and repository identity deduplicated by node_id.

A configuration can be one-off or long running. For example, when the team wants to study browser operation tools, users may create one keyword configuration named browser operation tools - keyword with terms such as browser agent, web agent, browser automation, and computer use, and a separate Topic configuration named browser operation tools - topic with Topics such as browser-agent and browser-automation. Both can be manually run once; if results remain useful, users can switch them to weekly execution.

The discovered tools page must merge keyword, Topic, and manual add results. The default order is first discovery time descending, with tools in the same batch ordered by current Stars descending. The page must also provide transparent sorting by latest discovery, current Stars, and seven-day Stars growth. Seven-day Stars growth comes only from AI Cool's own stored snapshots for tools already in the pool. It must not create new tools, must not be labeled GitHub Trending, and must show unavailable when a suitable snapshot is missing. The seven-day calculation uses the snapshot closest to seven days ago within a six-to-eight-day window; the first week has no historical growth and growth starts after the second snapshot.

Each discovered candidate row must show repository name, one-line description, discovery source, current Stars, seven-day Stars growth, recent commit time, GitHub link, and actions to start evaluation or mark not handled. One-line description uses GitHub Description first. If the description is empty or too vague, AI Cool may generate a temporary Chinese summary from the beginning of README. Before a tool enters the team tools list, the evaluator must confirm the final one-line summary in the format of what it is, what problem it solves, and what scenario it fits.

Starting evaluation must be a UI action available only from discovered tools. The user manually enters evaluator, operator, and Cooper evaluation document link. AI Cool sets status to evaluating, stores evaluator and operator as user-entered text, stores start time, and stores the Cooper link. SSO, automatic identity binding, role-based access control, Cooper document creation, Cooper content reading, and Cooper permission validation are out of scope for the first release. AI Cool only validates that the stored Cooper URL belongs to the expected Cooper domain.

The Cooper evaluation document is owned by the user outside AI Cool. AI Cool must store only the URL. The recommended Cooper template has these sections: tool name and version; evaluation goal including why to evaluate and what real problem should be solved; usage environment including version, installation or integration method, account, cost, and permission needs; real task records including test task, operation process, actual result, and failure or manual takeover; conclusion including what problem can be solved, main limits and risks, and whether it should be included in team tools. This template is a recommended external document structure, not an in-app editor requirement.

Evaluating tools can finish only in two ways: included or excluded as not included. Completing as included stores result included, completion time, included time, and the evaluator-confirmed one-line summary; the tool becomes visible in the team tools list. Completing as excluded stores result excluded, completion time, not-included reason, excluded stage evaluating, and Cooper link; the tool does not enter the team tools list. A discovered tool marked not handled also becomes excluded, with excluded stage discovered and a not-handled reason.

The team tools list must show only tools whose status is included. It displays tool name, evaluator-confirmed one-line summary, GitHub link, Cooper evaluation link, and included time. The first release must not build complex category, rating, comment, recommendation-reason, community, voting, favorite, or tool-detail recommendation pages. Search and category can be revisited later only after real included tool volume proves the need.

Deduplication and status behavior are hard requirements. GitHub node_id is the stable unique key, so a repository rename or URL change must not create a second tool. When the same repository is found by multiple keywords or Topics, AI Cool stores one tool and merges discovery sources. Repeated matches update recent discovery or hit time. Repeated matches must not move evaluating, included, or excluded tools back to discovered. Excluded tools remain stored to prevent rediscovery loops, but are hidden from primary user lists.

Weekly Stars snapshots must be stored only for discovered, evaluating, and included tools. Excluded tools do not need new weekly snapshots. The discovery/run layer must record pagination counts, actual pages fetched, incomplete_results, truncation, GitHub rate-limit information, reset time when available, bad query failures, and other API errors. A run with partial or failed GitHub results must record the failure state without corrupting existing tool records or silently pretending the run was complete.

The implementation plan must follow the existing repository shape. The backend keeps the current Go plus PostgreSQL style, module-local schema.sql with EnsureSchema, shared pgxpool, publicapi handler style, and route registration from both HTTP entrypoints. The tools domain must be independent from existing raw_items and items because tool candidates need stable repository identity, merged discovery sources, status history, evaluations, and snapshots. The frontend keeps the current React, Vite, TypeScript, hash-route, and self-managed CSS approach, adding tools navigation for discovered tools, evaluating tools, team tools, and discovery configs. Deployment planning must include a discovertools command and weekly cron integration.

The closed-loop cases that must be derivable from the requirements are: create a keyword discovery configuration; create a Topic discovery configuration; edit a discovery configuration; enable or disable a discovery configuration; manually run a configuration; weekly run enabled configurations; manually add a GitHub repository URL; merge duplicate discoveries across keyword, Topic, and manual sources; start evaluation from a discovered candidate; mark a discovered candidate as not handled; finish evaluation as included; finish evaluation as not included; view the team tools list with only included tools; sort discovered tools by latest discovery, current Stars, and seven-day Stars growth; handle missing Stars growth snapshots; record GitHub limit, incomplete, bad query, and failure information; and reject or serialize invalid concurrent status operations such as starting evaluation twice or completing a non-evaluating tool.

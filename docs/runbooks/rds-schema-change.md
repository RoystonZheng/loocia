# RDS 数据库结构变更

## 适用范围

用于在公司 RDS MySQL 中创建或修改表、字段和索引。数据修复、批量 `UPDATE` 或 `DELETE` 不属于本手册，应使用经过审批的数据变更流程。

## 来源和时效

本手册提炼自 RDS 使用规范、DDL 工单说明和控制台快照，尚未把 2026-08-11 标记为真实生产变更验证。控制台入口、审核角色和风险分级可能变化，提交前以平台当前展示为准。

## 必要输入

- 目标环境 `<ENV>`、RDS 服务 `<RDS_SERVICE>`、数据库 `<DATABASE>` 和表 `<TABLES>`。
- 当前结构、MySQL 版本、表数据量、访问量和全部分表范围。
- 正向 DDL、兼容性说明、执行窗口、验证 SQL。
- 可执行的回滚 DDL；不可安全回滚时，提供前向修复方案。
- 下游使用方和审批责任人。

任何一项无法确认时，不提交生产变更。

## 平台强制约束（MUST）

- 库、表、字段名使用小写和下划线，不使用 MySQL 关键字。
- 表和字段必须有清晰注释。
- 每张表必须有与业务无关的自增主键，类型为 `BIGINT UNSIGNED`。
- 禁止外键、自定义函数、触发器、存储过程和视图。
- 普通字段使用 `NOT NULL` 和显式默认值；`TEXT`、`BLOB`、`JSON` 等按类型能力处理，不伪造非法默认值。
- 普通索引以 `idx_` 开头，唯一索引以 `uniq_` 开头。创建索引使用 `ALTER TABLE ... ADD INDEX`，不使用 DDL 工单不支持的 `CREATE INDEX` 形式。
- 字符集使用库允许的 `utf8` 或 `utf8mb4`，不随意覆盖库级排序规则。
- 时间字段使用合法默认值，优先评估 `DATETIME`，避免忽略 `TIMESTAMP` 的范围限制。
- 分表命名为 `<table>_<natural_number>`，禁止多级分表；所有分表的结构必须一致变更。
- 临时表以 `temp_` 开头，且不得与正式表或分表重名。
- 字段类型或语义变化前必须确认数据链路和全部下游使用方。
- `DELETE`、`UPDATE` 必须带有效 `WHERE`，禁止超大事务；这类操作不混入 DDL 工单。

## 团队变更前检查（SHOULD）

1. 从当前数据库读取 `SHOW CREATE TABLE` 和相关索引，不只依赖仓库里的旧 DDL。
2. 核对项目迁移规则，保证平台执行记录和代码仓库迁移文件表达同一变更。
3. 检查 SQL 对当前 MySQL 版本兼容，不使用仅新版本支持的语法。
4. 评估全表扫描、锁表、重建索引、磁盘增长、主从延迟和执行时长风险。
5. 检查旧代码能否读取新结构，新代码能否兼容变更前结构。优先采用可滚动发布的 expand/contract 方案。
6. 涉及分表时列出完整分表集合，并验证批量展开结果。
7. 准备执行后结构、数据样本、业务接口和监控验证。
8. 生产变更前向用户展示目标、SQL 摘要、风险、执行窗口和回滚或前向修复方案，取得明确确认。

## 提交 DDL 工单（CHECK）

1. 打开 RDS 控制台，进入 `DDL 工单 -> 新建工单`。
2. 选择目标数据库，逐项核对服务名、账号、库名和环境。预期结果：页面目标与必要输入完全一致。
3. 粘贴单一目的的 DDL，不夹带无关变更。预期结果：SQL 可以被平台完整解析。
4. 执行语法检查和语义分析。任何警告都要解释或修正，不以“可以提交”代替风险判断。
5. 选择符合风险和窗口要求的执行方式，填写变更原因、影响范围、验证方式和回退方案。
6. 提交审核。审核链路和风险等级以平台当前展示为准，不绕过平台或 DBA 要求。
7. 审核通过后按批准窗口执行，持续观察工单状态、数据库指标和业务告警。

## 执行后验证

- 用 `SHOW CREATE TABLE`、`SHOW INDEX` 或等价元数据查询确认结构和索引与目标一致。
- 确认全部分表结构一致，没有漏表或部分失败。
- 执行小范围、走索引的验证查询，确认默认值、约束和兼容性。
- 验证关键接口、任务或消费链路，不只验证 SQL 成功。
- 检查数据库负载、慢查询、主从延迟、错误率和业务告警。
- 保存工单链接、执行时间、最终 SQL、验证摘要和相关代码提交。不要保存敏感数据结果。

## 失败处理和回滚

- 未执行：修正 SQL 或变更方案后重新预检，不反复提交同一错误工单。
- 部分执行：停止后续步骤，保留平台状态和数据库证据，联系 DBA 确认已生效范围。
- 已执行且可逆：仅在验证过回滚 DDL 的锁表和数据风险后执行回滚。
- 删除字段、收窄类型、唯一约束等不可安全逆转：不要声称可以回滚，使用事先准备的前向修复方案，并同步应用发布策略。
- DDL 通常隐式提交。不能依赖事务回滚来撤销结构变更。
